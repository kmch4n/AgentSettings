# sanitize-artifacts スキル

対話を通じて生成した成果物から制作過程の痕跡を取り除き、想定読者にとって自然な単体の納品物に整える。

## 適用タイミング

- 反復的なプロンプト、修正指示、例示、制約の追加を経て作られた成果物を仕上げるとき
- ドキュメント・README・手順書・提案書・スライド原稿などを第三者へ渡す直前
- 「なぜこう書かれているか」を説明する文が本文に混ざっている疑いがあるとき

コードの機能修正やリファクタリングには使わない。対象は読者に読ませる文章・ドキュメントである。

## 引数の処理

`$ARGUMENTS` に対象ファイルまたはディレクトリを指定する。
引数がない場合は、直近のセッションで生成・編集した成果物を候補として提示し、対象を確認する。

## 中核原則

対話は制作コンテキストであって、そのまま成果物の内容になるわけではない。
本文に残すかどうかを判断する前に、各記述を次の3つに分類する。

1. **読者が本当に必要とする内容** — そのまま残す
2. **成果物に影響させるべき制作上の指針** — 構成・トーン・粒度・既定値・例・命名へ反映し、文としては消す
3. **対話の残骸** — 削除する

本文に直接現れてよいのは 1 だけである。

## ステップ1: 対象の把握

対象ファイルを Read で読み、想定読者・目的・成果物の種類を確定する。
読者が誰かを言語化できないうちは削除判断を始めない。

## ステップ2: 混入パターンの検出

以下の表現を Grep と通読の両方で洗い出す。日本語と英語のどちらでも同じ機能を持つ表現を探す。

| 種類 | 日本語の例 | 英語の例 |
| --- | --- | --- |
| 指示の引用 | ご指示のとおり / 依頼に基づき | As requested / Based on your instruction |
| 除外の宣言 | ○○は使用しません / ○○は避けています | We will not use / This avoids |
| 版の比較 | 前回の版と異なり / 修正前は | Unlike the previous version / This was changed to |
| 制作意図の説明 | この節を追加した理由は / 要件を満たすため | This section was added because / To satisfy the requirement |
| 対話への言及 | ユーザーの希望により / プロンプトでは | The user wanted / The prompt says |
| 不要な前提宣言 | 本書は○○を前提とします | This document assumes |

機械的に消さない。読者が本当に知る必要のある前提・制約だけは残す。

## ステップ3: 制約を設計へ変換する

制約は原則として成果物の設計に反映し、断り書きとしては出さない。

| 制作時の制約 | 本文への正しい反映 |
| --- | --- |
| 「Git や CLI は使わない」 | 「共有フォルダを Google Drive に置く」と手順そのものを書く |
| 「専門用語を避ける」 | 平易な語彙に置き換える（避けた旨は書かない） |
| 「初心者向けに」 | 説明の粒度・用語の定義・例の密度で表現する |
| 「○○には触れない」 | ○○を書かない（触れない旨も書かない） |

悪い例:

> 本ガイドでは Git や Homebrew、追加の CLI ツールは使用しません。

良い例:

> プロジェクトフォルダは Google Drive で共有します。

## ステップ4: 例示の扱い

ユーザーが意図を伝えるために出した例は、成果物自体がその例を必要としない限り本文へ持ち込まない。
対話中の例は診断材料であり、最終成果物の題材ではない。

例からは次を読み取り、内容ではなく設計へ反映する。

- 期待される抽象度
- 想定読者とトーン
- 排除すべき不自然な言い回し
- 効いている設計上の制約

## ステップ5: 検査チェックリスト

- [ ] 対話を見ていない読者にとって自然に読めるか
- [ ] 「なぜこう書かれたか」を説明している文が残っていないか
- [ ] 不要なツール名・除外事項・代替案への言及がないか
- [ ] プロンプト内の例が成果物の題材になっていないか
- [ ] 複数回の修正による継ぎ接ぎの跡がないか
- [ ] トーン・用語・前提が全体で一貫しているか
- [ ] 見出しと注記が制作者ではなく読者に向いているか
- [ ] 制作過程にしか属さないメタ発言が残っていないか
- [ ] 断り書きが、読者に本当に必要な場合だけに絞られているか
- [ ] 全体を通して声（文体・人称・敬体常体）が一つに揃っているか

## 出力ルール

- 説明するより書き直す。削除だけでなく、必要なら自然な文へ再構成する。
- 修正後の成果物そのものを出す。「メタ記述を削除しました」「整えた版です」のような前置きは付けない。
- 変更点の要約は、ユーザーが求めたときだけ、成果物の後ろに付ける。
- 成果物の目的・技術的正確性・読者に必要な要件は必ず保持する。

## 注意事項

- 削除の判断に迷ったら、消さずにユーザーへ該当箇所を示して確認する。
- 契約・法務・安全に関わる注意書きは、制作過程の痕跡に見えても原則として残す。
- 元ファイルを直接書き換えるため、未コミットの変更がある場合は事前にユーザーへ知らせる。
